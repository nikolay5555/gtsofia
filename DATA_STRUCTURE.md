# Структура на генерираните данни

`Scripts/generate_transport_data.py` е кратката входна точка. Логиката е разделена в `Scripts/lib/` по отговорности:

- `common.py` — пътища, нормализация на ID и дати;
- `gtfs.py` — сваляне и четене на GTFS;
- `calendar.py` — активни услуги и календарни изключения;
- `stops.py` — OSM-first имена/координати със GTFS fallback;
- `trips.py` — курсове и времена по спирки;
- `direction_patterns.py` — разпознаване на направления и сливане на частични курсове;
- `direction_output.py` — крайни направления и дестинации;
- `schedules.py` — разписания;
- `shapes.py` — геометрия на маршрутите.

Файловете под `data/` са разделени по предназначение:

| Файл | Съдържание |
|---|---|
| `metadata.json` | Дата на обновяване, източник, настройки на линиите |
| `routes.json` | GTFS линии |
| `stops.json` | Спирки, OSM-first имена/координати и GTFS fallback |
| `trips.json` | Само курсове за услуги, активни в генерирания календарен период |
| `directions.json` | Направления, крайни спирки и дестинации |
| `schedules.json` | Часове на пристигане по направление и тип ден |
| `calendar.json` | Календарни модели и дневни индекси за текущия период |
| `calendar-exceptions.json` | GTFS изключения, групирани по дата вместо повторение на пълен обект за всеки ред |
| `shapes.json` | Геометрия от GTFS; публикува се отделно и не се зарежда от страниците, защото в момента те не я визуализират |

`transport-data.js` зарежда необходимите JSON файлове паралелно и ги събира в `window.transportData`. Така страниците продължават да използват същата структура в паметта, без да свалят един общ 65 MB файл.

## Обновяване

```bash
python Scripts/generate_transport_data.py
```

Скриптът атомарно записва всеки JSON файл и премахва остарелия `data/transport.json` след успешно записване. GitHub Actions добавя/комитва всички промени в `data/`.

## Дестинации във виртуалните табла

Дестинацията на показаната линия се определя от името на крайната спирка за конкретния курс. Таблото първо използва името на действителната крайна спирка от `stops.json` — OSM има приоритет при съвпадение, а GTFS остава резервен източник за спирки без използваемо име в OSM. При съкратен/заместващ реалновременен курс се използва неговата действителна крайна спирка. Ако тази спирка не може да бъде намерена в индекса, таблото предпочита GTFS етикета за реалновременния курс пред крайната спирка на пълното статично направление, за да не показва грешна дестинация.
